# Playwright Field Guide v0.1.0

**Release status:** Candidate pending final CI and merge  
**Release date:** TBD

## What v0.1 establishes

v0.1 turns the repository from an initial concept into a production-minded Playwright engineering reference with three ways to use it:

- **deep guides** for engineering decisions and tradeoffs;
- **quick references** through recipes, FAQ, and anti-patterns;
- **living validation** through executable examples and freshness automation.

## Core coverage

### Reliability

- test isolation and deterministic design;
- synchronization and web-first assertions;
- retry misuse and fixed-wait anti-patterns;
- a structured flakiness diagnostic workflow.

### Locator strategy

- role, label, text, and test-ID decisions;
- filtering and scoping;
- dynamic UI patterns;
- fragile vs resilient locator examples.

### Fixtures, authentication, and test data

- fixture vs hook decisions;
- worker scope;
- authentication-state strategies;
- parallel-safe data ownership;
- API-assisted setup and data factories.

### Architecture

- Page Object decision guidance;
- component objects and workflow/domain layers;
- composition vs inheritance;
- suite structures from small to production scale.

### CI and debugging

- diagnosable GitHub Actions patterns;
- Trace Viewer and artifact strategy;
- retries, workers, sharding, and resource pressure;
- a dedicated passes-locally/fails-in-CI workflow.

### API and advanced Playwright

- API-only, UI-only, and hybrid test boundaries;
- network interception and mocking;
- downloads/uploads;
- popups, frames, and multiple pages.

### Daily reference

- FAQ;
- Field Recipes;
- Anti-pattern Catalog.

## Living-documentation foundation

v0.1 also introduces:

- a pinned Playwright dependency;
- a committed npm lockfile;
- executable examples;
- pull-request and `main` executable-documentation CI;
- weekly freshness validation;
- Dependabot dependency signals;
- a human-reviewed Playwright release-maintenance process.

## Editorial contract

The Field Guide distinguishes:

- **Official Playwright guidance**;
- **Engineering recommendation**;
- **Context dependent** decisions.

This distinction is intentional. The project should not present an opinionated framework choice as though Playwright itself requires it.

## Relationship to official documentation

The Field Guide supplements, rather than replaces, Playwright's official documentation. Official behavior and recommendations should be linked to authoritative upstream material; this project focuses on engineering judgment, failure modes, tradeoffs, and practical application.

## After v0.1

Post-v0.1 work should be driven by observed value rather than taxonomy completion. Likely sources include:

- Playwright releases that materially affect test engineers;
- recurring community questions;
- reproducible failure modes;
- high-value recipes;
- gaps discovered while applying the guidance to real suites.

The project should remain a field guide, not grow into a competing Playwright framework.
